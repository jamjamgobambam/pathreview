## Solution plan

**Issue:** [Concurrent review requests for the same profile can produce inconsistent results](https://github.com/ascherj/pathreview/issues/82)

### Understand
`process_review()` in `core/services/review_service.py` has several `await` points (DB reads/writes), and nothing stops two calls to it from running for the same `profile_id` at the same time. FastAPI's `BackgroundTasks` run in-process on the same single-threaded asyncio event loop as the web server — they are not a separate worker/queue — so two review requests submitted back-to-back for the same profile become two coroutines the event loop is free to interleave at every `await`. Right now, `_run_ingestion_pipeline()` is the only step that actually touches profile-scoped shared state (it inserts `IngestedSource` rows), so it's the one place today where this interleaving is directly observable.

**Expected behavior:** If review 1 and review 2 are both submitted for the same profile, review 2 should not start touching that profile's data until review 1 has completely finished (committed) and released its hold on that profile. Review 1 should never see any change review 2 makes, and vice versa, no matter which one was submitted first or which one's individual DB statements happen to run faster. Reviews for two *different* profiles should keep running fully concurrently — the fix must not become a lock on the whole app.

**Actual behavior (today):** No serialization exists. Two reviews for the same profile can have their DB reads/writes interleaved arbitrarily. This is directly confirmed by the two integration tests in `tests/integration/test_concurrent_reviews.py` — both currently fail because the reviews' database-writing windows overlap instead of running one after the other.

### Map
- `core/services/review_service.py` — `process_review()` is where the lock goes; `_run_ingestion_pipeline()` is the step it protects.
- `api/routes/reviews.py` — the endpoint that schedules `process_review()` as a background task (not expected to change, but confirmed to exist as the caller).
- `tests/integration/test_concurrent_reviews.py` — the two reproduction tests this fix needs to make pass, with no changes required to the tests themselves.

**Decided:** the lock wraps the entire `process_review()` body (from fetching the review/profile through the final commit, including the exception-handling path), not just `_run_ingestion_pipeline()`. This is the safer choice if a future step besides ingestion ever starts touching shared profile-scoped state.

**Revised decision:** the lock must work correctly across multiple threads, processes, and instances, not just within a single uvicorn worker. That rules out an in-process Python object (a `dict` of `asyncio.Lock`s, or any `threading.Lock`) as the mechanism — none of those are visible outside the one process that created them, so two separate instances (or workers) would each enforce their own private lock and never actually serialize against each other. The lock state has to live somewhere every instance can see and agree on.

Given that, **Redis is the better fit over a Postgres advisory lock** for this codebase specifically:
- Redis is already provisioned (`docker-compose.yml`, `settings.redis_url` in `core/config.py`) and already used for other cross-cutting concerns (`safety/rate_limiter.py`, `agent/memory/session_store.py`, `api/routes/health.py`).
- A Postgres advisory lock (`pg_advisory_lock`/`pg_advisory_xact_lock`) would require either pinning one specific pooled connection for the lock's entire hold duration (session-scoped locks release when their connection closes, and SQLAlchemy's pool doesn't guarantee the same underlying connection stays with you), or restructuring `process_review()`'s current multiple-`await db.commit()` pattern into one single wrapping transaction (transaction-scoped locks auto-release at commit). Redis's lock is independent of the DB transaction boundaries entirely, so it drops in around the existing multi-commit structure without restructuring it.

**Important caveat:** every existing Redis usage in this codebase (`RateLimiter`, `SessionStore`, the health check) uses the synchronous `redis.Redis` client, called directly inside async functions. That's fine for the quick, one-off calls those make, but a lock held for the full duration of `process_review()` needs the async client (`redis.asyncio.Redis`) instead, so it doesn't block the single-threaded event loop while waiting on lock acquisition/release. This is a new pattern for this codebase, not a copy of the existing sync usage.

### Plan
1. Add an async Redis client (`redis.asyncio.Redis.from_url(settings.redis_url)`) available to `core/services/review_service.py` — separate from the existing synchronous `redis.Redis` client used elsewhere in the codebase.
2. Wrap the full body of `process_review()` (steps 1–6, including the existing exception handler) in `async with redis_client.lock(f"profile-lock:{profile_id}", timeout=<TTL>):`, using `redis.asyncio`'s built-in `Lock` helper, so the lock is held for the entire duration of one review's processing and is released even if the function raises.
3. **Decided (default, not tuned):** use a 60-second lock TTL for now. Today's `process_review()` runs entirely against stubs for agent orchestration and RAG retrieval/generation (no real LLM or vector DB calls yet), so it completes in well under a second — 60 seconds is deliberately generous headroom, not a measured value. This will need revisiting once those steps make real LLM/vector-DB calls, which could plausibly run much longer. Not worth tuning precisely right now (see Risks).
4. **Decided:** fail closed if Redis is unreachable when acquiring the lock — unlike the existing `RateLimiter`'s fail-open behavior, a failed lock acquisition here should route into the existing exception-handling path in `process_review()` (mark the review `"failed"`, don't process it) rather than silently proceeding without a lock. Log the failure explicitly (e.g. `log.error("profile_lock_acquire_failed", profile_id=..., error=...)`) so a Redis outage is distinguishable in the logs from other kinds of review failures, rather than looking like a generic error.
5. Run `tests/integration/test_concurrent_reviews.py` and confirm both existing tests still pass — they assert on observable behavior (serialization + non-blocking of independent profiles), not on the specific lock implementation, so they should be implementation-agnostic and need no changes.
6. Add a new test covering the exception path: a review that raises partway through must still release its profile's lock, so a failed review doesn't permanently block later reviews for that profile (currently untested).

### Inputs & outputs
**Input:** the `profile_id` a given `process_review()` call is operating on — already a parameter, no signature change needed.
**Output/change:** no change to the API contract or response shape. This is purely an internal execution-ordering guarantee: after the fix, two `process_review()` calls for the same `profile_id` always run one at a time; calls for different `profile_id`s continue to run concurrently, unaffected.

### Risks & unknowns
- Deduplication of `IngestedSource` rows is explicitly out of scope for this fix (confirmed earlier in this project) — the lock solves *ordering*, not the separate missing-dedup-check bug where `_run_ingestion_pipeline()` inserts unconditionally with no existence check. Worth calling out in the PR description so reviewers don't expect duplicate rows to stop appearing.
- **Lock TTL (default chosen, not tuned):** set to 60 seconds for now, purely as generous headroom over today's stub-only pipeline runtime (well under a second). Not a measured or carefully-tuned value — once agent orchestration and RAG retrieval make real LLM/vector-DB calls, actual run times should be measured and this revisited. Too short risks the lock expiring mid-run and being "stolen" by a waiting review (recreating the exact race this fix exists to close); too long means a crashed/hung review blocks that profile for longer than necessary. Acceptable to leave as a rough default for now.
- **Redis failure behavior (decided):** fail closed — if Redis is unreachable when `process_review()` tries to acquire the lock, the review is marked `"failed"` (via the existing exception-handling path) rather than proceeding unprotected, and the failure is logged explicitly. This is a deliberate departure from the existing `RateLimiter`'s fail-open convention: fail-open there only costs a temporary rate-limit overage, but fail-open on a mutual-exclusion lock would silently reintroduce the original race whenever Redis has a hiccup. One consequence worth being aware of: a Redis outage now means *no* reviews can be processed at all (for any profile) until it recovers, rather than just losing the concurrency protection — an intentional availability-for-correctness trade-off.
- **No strict FIFO fairness:** the earlier in-process `asyncio.Lock` design guaranteed waiters are served in the order they asked (a FIFO queue). A Redis lock built on `SET NX` + retry/polling (what `redis.asyncio`'s built-in `Lock` uses) does not guarantee acquisition order among multiple waiters for the same profile — mutual exclusion still holds (only one holder at a time), but which waiting review goes next isn't guaranteed to be first-come-first-served. Worth confirming this is acceptable, since nothing in the issue or the existing tests requires ordering, only exclusivity.
- A process that crashes outright (killed, OOM, etc.) while holding the lock behaves differently than a process that raises an exception. An exception is caught by `async with`, releasing the lock immediately. A hard crash leaves the Redis key in place until its TTL expires — nothing else can release it early, unlike the earlier in-process design where the lock would vanish along with the crashed process's memory automatically.
- Each review holds an open `AsyncSession` (from a pool of `pool_size=10, max_overflow=20` — see `core/database.py`) for its entire duration, including any time spent blocked waiting for another review's lock. If enough reviews are in flight at once across many profiles, those idle-but-blocked sessions could exhaust the 30-connection pool and cause unrelated requests to fail with a pool-timeout. This is a connection-pool capacity question tied to total concurrent in-flight requests, not a correctness issue with the lock itself.

### Edge cases
- Two reviews for the same profile — covered by `test_concurrent_reviews_are_serialized_by_profile_lock`.
- Reviews for two different profiles submitted at the same time — must not serialize against each other — covered by `test_independent_profile_is_not_blocked_by_unrelated_profile_lock`.
- A review that fails/raises partway through while holding the lock — not yet tested by either existing integration test (both only exercise the success path); planned as new test coverage above.
- More than two reviews queued for the same profile at once (3+): mutual exclusion still holds regardless of waiter count, but (per the fairness point above) the *order* they're served in is no longer guaranteed FIFO the way the earlier in-process design would have been. No separate test planned for the exclusion property itself; ordering isn't a requirement here.
- The process holding the lock dying outright rather than raising — the Redis key would remain held until TTL expiry rather than releasing immediately. Not yet tested, and depends on the TTL decision above.
- Redis itself being temporarily unreachable — per the decision above, the review should end up `"failed"` with an explicit log entry rather than silently proceeding without the lock. Not yet tested (would need to simulate a Redis connection error, e.g. by pointing the client at a bad URL or mocking the acquire call to raise).
