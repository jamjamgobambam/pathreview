# Solution plan

**Issue:** [#147 — Resume section detection fails on text with leading whitespace](https://github.com/ascherj/pathreview/issues/147)

## Understand

`ResumeParser._detect_sections()` in `ingestion/parsers/resume_parser.py` is supposed to scan resume text and report which standard sections it finds (Experience, Education, Skills, etc.). Its regex patterns anchor on `^` (start of line, in `re.MULTILINE` mode) or immediately after `\n`, with no allowance for whitespace before the header text. Real-world input commonly has that leading whitespace — PDF-extracted text often carries indentation artifacts, and indented markdown source does too — so `detected_sections` comes back as an empty list even when a human reader can clearly see "Experience:", "Education:", and "Skills:" headers.

The same root cause independently breaks `_strip_markdown()`: its header-stripping regex (`r"^#+\s+"`, `re.MULTILINE`) also anchors to the exact start of a line, so an indented markdown header like `## Experience` (with 4 leading spaces) is never recognized as a header and never gets its `##` stripped.

**Expected behavior:** section headers are detected (and markdown headers stripped) regardless of leading whitespace/indentation.
**Actual behavior:** any leading whitespace before a header line causes that header to be silently skipped, in both `_detect_sections()` and `_strip_markdown()`.

## Map

- `ingestion/parsers/resume_parser.py`
  - `_detect_sections()` (~lines 127–146) — the 4 regex patterns built per section (lines ~134–138) need leading-whitespace tolerance.
  - `_strip_markdown()` (~lines 99–125) — the header-removal regex (line 102, `r"^#+\s+"`) needs the same fix.
- `tests/unit/test_resume_parser.py` — 6 currently-failing tests should pass after the fix: the 5 pre-existing ones (`test_parse_single_column_resume_text`, `test_parse_resume_no_work_experience`, `test_detect_sections`, `test_parse_markdown_resume`, `test_strip_markdown_syntax`), plus `test_parse_pdf_with_indented_sections`, a new regression test already added this week covering the PDF ingestion path specifically.
- `tests/conftest.py` — `sample_resume_text` fixture (lines 6–22) is itself indented (4 spaces per line, from the triple-quoted string), which is what currently triggers the bug in `test_parse_single_column_resume_text`.

## Plan

1. Update the 4 regex patterns in `_detect_sections()` (resume_parser.py:134–138) to tolerate leading whitespace on each line — e.g. `^{section}` → `^[ \t]*{section}` and `\n{section}` → `\n[ \t]*{section}`.
2. Update `_strip_markdown()`'s header regex (resume_parser.py:102) from `r"^#+\s+"` to `r"^[ \t]*#+\s+"` so indented markdown headers are also stripped before section detection runs on the cleaned text.
3. Re-run `.venv/bin/pytest tests/unit/test_resume_parser.py -v` and confirm all 6 currently-failing tests pass, and the 5 currently-passing tests still pass (no regressions). Baseline already established pre-change: full `make test-unit` run (`.venv/bin/pytest tests/unit -v -m unit`) shows **54 failed, 375 passed** across the whole suite, but only 6 of those 54 belong to `test_resume_parser.py` — the other 48 (across ~15 unrelated modules: `test_pii_scrubber.py`, `test_review_service.py`, `test_skill_extractor.py`, etc.) are pre-existing failures unrelated to this issue. After the fix, the target is exactly 48 failed / 381 passed — my change should move only the 6 resume-parser tests, not touch the other 48.
4. Add a new regression test asserting the specific leading-whitespace case from the issue (indented plain-text headers, tabs as well as spaces) plus a negative case guarding against false positives (e.g. an indented bullet line that mentions a section keyword mid-sentence, like `- Discussed skills growth` (with 2 leading spaces), should not register as a "Skills" section). Assert via membership checks (`any(... in ...)`), not list order or equality — `_detect_sections()`'s final `list(set(detected))` (resume_parser.py:146) doesn't guarantee ordering, and the existing tests already follow this pattern deliberately.
5. **Already done this week:** added `test_parse_pdf_with_indented_sections` through the **PDF path specifically** (`parser.parse(pdf_bytes)`, mocking `PdfReader` the same way `test_parse_multipage_pdf` already does), with a mocked page returning indented section headers. The issue names PDF-extracted text as the real-world trigger, but none of the originally-failing tests exercised `_parse_pdf()` — they were all markdown/plain-text input. This test currently fails (red), confirming the same bug reproduces through the PDF code path; it will pass once steps 1-2 are implemented. Without it, the fix could pass every other test while still being unverified through the actual code path the bug report describes.
6. Run `make check && make test-unit` (per `docs/CONTRIBUTING.md`) before opening the PR, to catch lint/type issues the unit tests alone wouldn't.

## Inputs & outputs

- **Input:** raw text (`str`) passed to `_detect_sections(text)` and `_strip_markdown(content)` — specifically strings containing leading whitespace/indentation before section-header or markdown-header lines.
- **Output:** `_detect_sections()` returns `list[str]` of detected section names (title-cased) — after the fix, indented headers are included in this list the same as unindented ones. `_strip_markdown()` returns cleaned `str` text with markdown syntax removed — after the fix, indented markdown headers are stripped like unindented ones. No function signatures change; only which input strings match.

## Risks & unknowns

- Loosening `^` to allow leading whitespace could over-match if a section keyword appears indented mid-sentence rather than as a real header (e.g. `- See skills section above` with 2 leading spaces) — need to verify the existing punctuation-anchored patterns (`\s*[:|-]` / `\s*$`) still constrain this correctly. Tied to `resume_parser.py:134–138`; will verify with the negative test case in Plan step 4.
- Using `\s*` instead of `[ \t]*` for the whitespace-tolerance fix would risk `\s` matching across newlines (since `\s` includes `\n`), potentially swallowing blank lines before a header — plan is to use `[ \t]*` specifically to stay within a single line, but need to confirm this doesn't miss any real indentation style during implementation.
- Unknown: whether "leading whitespace" in the issue is meant to include tabs, or only spaces — existing tests and the fixture only use spaces. Plan is to support both since it costs nothing extra with `[ \t]*`, but will flag this assumption in the PR description.
- **Resolved:** whether `[ \t]*` covers what `pypdf`'s `extract_text()` actually produces for an indented PDF. Tested directly: generated a real PDF from indented plain text (`cupsfilter` text-to-PDF, monospace layout — 4/8-space indents plus a tab) and ran it through `pypdf.PdfReader(...).extract_text()`. Result: indentation came back as plain ASCII spaces (`0x20`) only — tabs were expanded to spaces by the renderer before reaching the PDF, and no non-breaking space (`\xa0`) or other Unicode whitespace appeared anywhere in the extracted text. **Decision: keep `[ \t]*` as-is, do not add `\xa0`** — no evidence it occurs, and adding an untriggered character class would be speculative. Caveat: this used one text-to-PDF renderer (fixed monospace font); a resume built with a proportional-font tool (Word/Google Docs export, resume-builder templates) wasn't tested and could in principle lay out indentation differently — noted as a residual, lower-probability gap rather than a blocking unknown.
- **Resolved (was miscategorized):** the `\r`-from-Windows-line-endings risk. Re-examined the mechanics: in a CRLF (`\r\n`) file, `\r` attaches to the **end** of the preceding line, immediately before the `\n` — not after the `\n` and before the next line's indentation as originally written here. Confirmed with a regex test (`text = "Header:\r\n    Skills:\r\n"`): the existing `\n[ \t]*skills\s*[:|-]` pattern matches this input fine, because `[ \t]*` only needs to skip the leading spaces on the `Skills:` line — the stray `\r` never sits in that gap. **Decision: no character-class change needed; `[ \t]*` already handles CRLF input correctly.**
- Unknown: whether `_strip_markdown()`'s other regexes (bold, italic, links, inline code) have similar anchoring issues — a first read-through suggests only the header regex is anchored to line-start, but this needs to be double-checked against the full method before considering the fix complete.
- Risk: `make check` (the pre-PR gate named in `docs/CONTRIBUTING.md` and Plan step 6) is not sufficient on its own to guarantee the commit will pass. Confirmed `make typecheck` in the Makefile only runs mypy against `api/ core/ ingestion/ rag/ agent/ safety/` — it excludes `tests/` entirely — while the `mypy` pre-commit hook (`.pre-commit-config.yaml`) has no such exclusion and does check test files against `pyproject.toml`'s `disallow_untyped_defs = true`. Hit this directly this week: `make check` would have reported clean while the actual commit-time hook blocked on 12 missing type annotations in `test_resume_parser.py`. Takeaway: run an actual `git commit` (or `pre-commit run --files <changed files>`) before assuming `make check` alone means the PR is ready, especially for any test file changes in Week 9.
- **Resolved:** `make check`/`make typecheck` currently fails outright (a repo-wide numpy/mypy version-drift crash, unrelated to this fix) before it can even evaluate `resume_parser.py`. See "Out of scope" below for the root cause and decision — not fixing it here; the meaningful verification signal for #147 is `make test-unit`, which passes cleanly (12/12 in `test_resume_parser.py`, 48 pre-existing unrelated failures unchanged suite-wide).

## Edge cases

- Indented plain-text header with a colon, e.g. `Skills: Python, JavaScript` (with 4 leading spaces) — must still detect "Skills".
- Indented markdown header, e.g. `## Experience` (with 4 leading spaces) — must be stripped by `_strip_markdown()` and subsequently detected by `_detect_sections()`.
- A section keyword appearing indented but not as an actual header, e.g. `- Discussed skills growth` (with 2 leading spaces) — must NOT be falsely detected as a "Skills" section.
- Mixed indentation within one resume (some section headers indented, others flush-left) — all should be detected consistently, not just the flush-left ones.
- Leading whitespace using tabs (`\t`) rather than spaces — should be handled the same way as space-indentation.
- Dash-bullet-style section headers (e.g. `- Experience` instead of `Experience:`) — verified this is **not detected today and will not be detected after this fix either**; `_strip_markdown()` only strips `#`-style headers, and `_detect_sections()`'s patterns don't tolerate a `-` between the anchor and the keyword the way they tolerate whitespace. Deliberately left unhandled: teaching the parser to recognize a bullet as a header would require distinguishing it from an ordinary bullet point (e.g. `- Discussed skills growth`, the false-positive case above) — that's a real design decision outside this issue's whitespace-specific scope, not something this fix addresses.
- Hyphenated compound words starting with a section keyword (e.g. `Experience-driven leadership philosophy` or `Skills-based resume format`) — verified this **already false-positives today, independent of this fix**: `^experience\s*[:|-]` treats the `-` immediately after the word as valid header punctuation, with no way to distinguish it from a real header like `Experience - 2020`. This fix doesn't touch the `[:|-]` punctuation class at all (only adds leading-whitespace tolerance before the anchor), so the behavior is identical before and after. Noted here as a known pre-existing limitation, not something this fix is expected to resolve.

## Out of scope — possible future enhancement

`_detect_sections()` (resume_parser.py:134-138) and `_strip_markdown()`'s header regex (resume_parser.py:102) both hit the same leading-whitespace-anchoring bug independently, because each builds its own line-start regex rather than sharing one helper. A future enhancement could factor this into a single shared pattern/helper (e.g. a `_line_start(pattern)` builder) so this class of bug can't reappear a third time — not doing this now since it's a structural refactor beyond this issue's scope, but noting it in case a reviewer raises it.

**`make check`/`make typecheck` is broken repo-wide, independent of this fix — explicitly out of scope for #147.** Root cause: `pyproject.toml` pins `numpy>=1.26.0` with no upper bound, and a fresh install today resolves to numpy 2.5.1, whose bundled stubs use `type`-statement syntax requiring Python 3.12+. `[tool.mypy]` still targets `python_version = "3.11"`, so mypy crashes immediately on the numpy stub (`Type statement is only supported in Python 3.12 and greater`) before it can check anything. Confirmed via `git stash` that this crash exists identically on `main` and predates this branch — not something this change caused or should fix. Confirmed via `mypy --python-version 3.12 api/ core/ ingestion/ rag/ agent/ safety/` that bumping the config just to see past the crash reveals **103 pre-existing type errors across 26 unrelated files** — far beyond a Tier 1 whitespace-bug PR's scope to absorb.
