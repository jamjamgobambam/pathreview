# Solution Plan

**Issue:** [Add a "feedback tone check" that ensures all generated feedback is written constructively](https://github.com/ascherj/pathreview/issues/69)

---

## Understand

**Root cause:** The review pipeline generates feedback sections using an LLM but has no step to verify the output is constructive. `ReviewGenerator.generate_section()` calls the LLM, parses the output, and returns the result directly. There is no check that the feedback is specific, actionable, or encouraging — vague, dismissive, or discouraging feedback reaches the user unchanged.

**Expected behavior:** Every feedback section returned by the pipeline should be constructive (specific, actionable, encouraging). If a section fails a tone check, it should be regenerated with stronger instructions before being returned.

**Actual behavior:** Feedback is returned verbatim from the LLM with no tone verification. A section like "Needs work." or "Your projects are terrible." passes through the pipeline unchecked.

## Plan

1. **Create `safety/tone_checker.py`**
   - Implement `ToneResult` dataclass with `is_constructive`, `reason`, `section_name`
   - Implement `ToneChecker` class with two modes:
     - `_llm_check()`: send feedback to LLM with a classification prompt, parse `CONSTRUCTIVE` / `NEGATIVE` verdict
     - `_heuristic_check()`: regex-based fallback for unit tests without a live API key
   - Fail open on LLM errors (return `is_constructive=True`) so API timeouts don't block reviews

2. **Hook `ToneChecker` into `ReviewGenerator.generate_section()`**
   - Instantiate `ToneChecker(llm_client=self.client)` in `__init__`
   - After parsing the LLM output, call `self.tone_checker.check(section_name, section.content)`
   - If `is_constructive=False`, retry once with a stronger system prompt: *"Always write specific, actionable, and encouraging feedback."*

3. **Write unit tests in `tests/unit/test_tone_checker.py`**
   - Heuristic mode: constructive passes, dismissive fails, vague fails, actionable keywords pass
   - LLM mode (mocked): CONSTRUCTIVE verdict → passes, NEGATIVE verdict → fails, API error → fails open

4. **Write reproduction tests in `tests/unit/test_tone_checker_reproduction.py`**
   - Document the exact gap: without tone check, dismissive and vague feedback pass through
   - Show the fix catches both cases

5. **Fix pre-existing mypy error in `rag/generator/output_parser.py`**
   - Add type annotation to untyped `sections = []` variables (required for `make check` to pass)

## Inputs & Outputs

**Input:** A `FeedbackSection.content` string — the raw text generated by the LLM for one review section (e.g., `skills_feedback`, `projects_feedback`).

**Output:** `ToneResult(is_constructive: bool, reason: str, section_name: str)` — a structured verdict. If `is_constructive=False`, `ReviewGenerator` discards the section and retries generation once with a stronger system prompt, then returns the new section regardless of the retry result.

---

## Risks & Unknowns

- **Latency:** Each section now makes up to 2 LLM calls (generation + tone check) and possibly a 3rd (retry). For a full review with 5 sections, worst case is 15 LLM calls instead of 5. Mitigation: the heuristic fallback avoids the extra call when no LLM client is configured.

- **LLM-as-judge reliability:** The tone classifier prompt may occasionally misclassify borderline feedback. If it's too strict, it could trigger unnecessary retries. Mitigation: fail open on errors and use `temperature=0.0` for the classifier to reduce variance.

- **Retry loop:** Currently retrying only once. If the retry also produces negative feedback, it's returned anyway to avoid blocking the pipeline indefinitely. A future improvement could loop up to N times.

- **Model availability:** `_llm_check()` hardcodes `openai/gpt-4o-mini`. If the configured model differs or the API key has no access, it falls back gracefully via the `except` block.

---

## Edge Cases

- **Empty feedback string:** Heuristic check catches this (too short, no actionable signal) → `is_constructive=False`
- **Feedback with mixed signals:** Contains both a negative word and an actionable keyword → negative pattern takes priority → flagged
- **LLM returns unexpected format:** Parser reads only the first line for the verdict; if it's neither CONSTRUCTIVE nor NEGATIVE, `is_constructive=False` (safe default)
- **API timeout / rate limit:** Exception caught → fail open → `is_constructive=True` → section returned as-is
- **Very long feedback:** No length cap on the tone check input; prompt stays within `max_tokens=100` for the classifier response only
