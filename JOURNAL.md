## Week 7 — Issue selection

**Issue link:** https://github.com/ascherj/pathreview/issues/6

**Issue title:** Duplicate embeddings generated when re-ingesting the same repository

**Tier:** [ ] Tier 1  [x] Tier 2  [ ] Tier 3

**Problem summary:**
PathReview's ingestion pipeline (`ingestion/pipeline.py`) is supposed to skip sources it has already processed, but both halves of its idempotency mechanism are stubs: `_record_ingested_source()` only writes a log line and never persists an `IngestedSource` row, and `_check_skip()` queries the ORM with the literal string `"IngestedSource"`, filters on a `source_id` column that doesn't even exist on the model, and silently swallows the resulting exception — so the skip check never skips. As a result, every re-upload of the same resume, README, or repo is re-parsed and re-embedded (paying the embedding provider again) and its vectors are re-written into ChromaDB; for repo metadata the dedup hash is computed over volatile fields like star counts, so "the same repo" always lands under new vector IDs and retrieval returns near-identical chunks with inflated scores. A successful fix makes ingestion idempotent: implement real bookkeeping on the `IngestedSource` model (`core/models/ingested_source.py`, plus an Alembic migration for the dedup key), wire `_check_skip()` and `_record_ingested_source()` to it, and hash only stable content — so re-ingesting an unchanged source becomes a recorded no-op with zero new embeddings.

#### Appendix — implementation notes

Not part of the check-in template; my own record of the decisions behind the change.

**Design decisions and tradeoffs:**
Three worth recording. First, I added a dedicated `source_id` column rather than reusing the existing `content_hash`. Reusing it needs no migration and works for the read path, but gives no database-level guarantee, so two concurrent workers both pass the skip check and both insert. Since `source_id` already embeds `profile_id` and a source-type prefix, one global unique index is exactly the right key and makes the concurrent case correct rather than merely unlikely. Second, I narrowed both exception handlers from `except Exception` to `except SQLAlchemyError`. This was the change I was least likely to make on my own and the one I'm most convinced by: the original bug *was* an `AttributeError` swallowed by a bare `except Exception`, so keeping a broad catch would have preserved the exact mechanism that hid the issue — a future refactor breaking the query would silently disable dedup again, just with a louder log line. There's now a regression test asserting an `AttributeError` propagates. Third, I accepted a known limitation: `RepoAnalyzer.parse()` bakes volatile stats into the embedded text, so a correctly-skipped re-fetch leaves a stale star count in the stored chunk. Refreshing stats is a re-ingestion policy question adjacent to #27, and I called it out in the PR rather than quietly widening scope.

**Comparison against other attempts:**
Before opening the PR I checked what else existed upstream. PR #324 claims #6 but contains only a reproduction test and a plan, no fix. PR #305 (issue #13) is a genuine near-parallel: same `select()` rewrite, same async conversion, same commit-inside-record decision, and it needs no migration. It does not fix the volatile repo hash, though — its diff still reads `self._hash_content(str(repo_data))` — so under it a repo re-fetched with one extra star still re-embeds, which is precisely the case this issue's title names. Its plan diagnoses that line as a dictionary-*ordering* problem, but sorting keys would not help, since a star count changing 41 to 42 alters the serialization at any key order. Reviewing it is what prompted the `SQLAlchemyError` narrowing above; the two PRs will conflict, and I offered to rebase onto whichever lands first.

**Review status and the type gate:**
No review yet at time of writing. Exactly one PR has ever merged into this repository (#176), so I'm treating an open, well-argued PR as the realistic outcome rather than a merge. On typing specifically: because `make typecheck` aborts before it checks anything, the pre-commit `mypy` hook is the only gate that actually runs, and I only discovered that when it blocked a commit. It initially reported 42 errors, roughly 30 of them mine, so I annotated both new test files rather than reaching for `--no-verify`. It now reports 12, every one pre-existing upstream. Commits touching Python still need `SKIP=mypy` to get past those, which I used in preference to `--no-verify` so that ruff and black still gated every commit.

**What I'd do differently:**
I lost time to a self-inflicted problem in the last mile: pasting a long PR body through a shell heredoc mangled it, and a stray newline ended up inside the PR title on a public repo. Writing the body to a file and passing `--body-file` — which is what finally worked — should have been the first move, not the recovery.
